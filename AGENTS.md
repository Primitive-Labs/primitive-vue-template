## Project Stack

- This project uses vite, typescript, vue, vue-router, pinia, tailwind, shadcn-vue, js-bao and js-bao-wss-client. Do not deviate from this stack. If there are additional foundational components required, ask the user before installing them.

## Project Organization

- `/src/assets`: Static images/assets
- `/src/components`: Vue Components. Organized by area.
- `/src/components/ui`: Installation location for base shadcn-vue components.
- `/src/config`: The app's environment-derived config and the client options (`envConfig.ts`). `storage.ts` keeps db3s on the device, in the browser's origin-private file system (OPFS): the storage engine's worker, its tab-sharing broker and the two wasm files it asks for. Import the worker and broker only as URLs (`?worker&url`, `?url`), never as constructors, so a test that imports the client options starts no worker.
- `/src/lib`: Shared business logic, not Vue specific -- pure typescript code only. `client.ts` owns the app's one client: `main.ts` calls `initializeAppClient(getJsBaoConfig())`, and everything else uses `await getAppClient()`.
- `/src/composables`: Vue composables (`useJsBaoDataLoader`, which loads data and reloads on model changes and on the client's `db3:ready` / `db3:gone` / `db3:evicted`).
- `/src/layouts`: Vue layout components. Used directly by the router to render different layouts for different types of pages based on route
- `/src/models`: Models generated by `pnpm codegen` from this app's db3 types (see "Database types" below). Never edit them.
- `/src/pages`: Top level Vue components that map to a route.
- `/src/router`: Vue-router configuration
- `/src/stores`: Pinia stores. The template ships only `userStore`: the signed-in user, sign-in (code, link, Google, passkeys), profile and avatar. App data belongs in the app's own stores or components, read through the generated models.
- `/src/tests`: `pnpm test` specs (vitest, in Node). `src/tests/support/signIn.ts` signs in the test account (`PRIMITIVE_TEST_EMAIL`) and returns a client.
- `/public`: Copied verbatim into `dist/` by Vite. `_headers` sets response headers on those assets (Cloudflare Workers static assets read it) — the one place for that, since `worker.js` is library-provided. `.well-known/apple-app-site-association` is what lets an iOS client of this same app open this domain's links: the emailed sign-in link is one `https://<domain>/oauth/callback` URL that opens the app where it is installed and signs in here otherwise. That document is NOT committed — `scripts/deploy.mjs` generates it before each build from the deployed Primitive environment's `iosAppId`, because an app has one bundle id per environment (`.well-known/apple-app-site-association.example` is only a reference copy). `.well-known/README.md` has the activation order — declare `iosAppId`, deploy, verify with `curl`, and only then enable the app's `applinks:` entitlement.

## General Coding Guidelines

- ALWAYS Fail early. Don't mask missing required inputs with inline fallbacks or try to recover from errors caused by improper usage or bad input. Expose the errors directly.
- ALWAYS use strong typing and invariants over scattered defensive code.
- ALWAYS run pnpm codegen and pnpm type-check after making changes and fix any errors.
- ALWAYS run pnpm lint after making changes and fix what it reports in the source. The lint uses the type-aware `recommendedTypeChecked` preset, so it reports unhandled promises, `async` functions that never await and redundant type assertions: `await` a promise, give it a `.catch`, or mark it `void` with a comment saying why fire-and-forget is intended (only when the callee handles every error it can raise). Do not add `eslint-disable` comments; a rule may be relaxed only in `eslint.config.ts`, scoped to a file pattern, with the reason beside it. Lint also warns on every use of a deprecated platform API (js-bao, js-bao-wss-client); replace it with what the `@deprecated` note names. A lint run with `--max-warnings 0` fails on those warnings too.
- NEVER modify worker.js. This is a library provided file and should not be edited.

## Using the Primitive Platform

- The Primitive CLI (`primitive-admin` on npm) is required for working with the Primitive platform. Install it globally with `pnpm add -g primitive-admin` (or `npm install -g primitive-admin` if you use npm — pick one manager, not both), then authenticate with `primitive login`.
- This project uses **project mode**: the nearest ancestor `primitive/config.json` — found by walking up from this directory the way git finds `.git` — defines named Primitive environments (e.g. `dev`, `prod`), each binding an `apiUrl` and `appId`. It is the SINGLE source of truth for the backend URL and app ID — NEVER author `VITE_APP_ID`, `VITE_API_URL`, `VITE_WS_URL` or `VITE_APP_NAME` in a `.env` file; the `primitiveEnv()` Vite plugin fills them from the resolved environment, and a deploy refuses to run when it finds one. Per-environment tokens live in `.primitive/credentials.json` and this machine's selection in `.primitive/local.json` (both gitignored). `primitive init` scaffolds a `dev` environment. It may sit in this directory or, when this client is one of several sharing one Primitive app, at the repo root above it — either way there is exactly ONE, and every `primitive` command run from anywhere inside the tree resolves it, so no command needs a path flag. If no config exists in this directory or any parent, create one with `primitive env add dev --api-url <url> --app-id <appId>`.
- Select the Primitive environment with `primitive env use <name>` (writes the gitignored local selection — no tracked file changes), or per command with `--env <name>` / `PRIMITIVE_ENV`. Resolution order: `--env` → `PRIMITIVE_ENV` → `.primitive/local.json` → the committed `defaultEnvironment` → the sole environment.
- Deploying names two independent things and neither defaults: `pnpm cf-deploy --deploy-env <name> --primitive-env <name>`. The DEPLOY environment is the front end (Vite mode + the `wrangler.toml` `[env.<name>]` section); the PRIMITIVE environment is the backend/app pair. Say "deploy environment" or "Primitive environment" — never a bare "environment". Add `--check` to print the resolved pair and the exact commands without running them. `--primitive-env` may name a child app's machine-local environment; add `--preview-alias <alias>` to upload a preview version against the child instead of replacing the live worker (the script registers the preview origin on the child), since a live deploy to a child warns that it replaces the worker for everyone. A mode that declares `VITE_EXPECTED_PRIMITIVE_ENV=<env>` also accepts a child whose tree is `<env>`.
- When another agent or worktree shares the Primitive environment, work on your own child app: `pnpm child:up <slug> [--port <n>]` creates or resumes it, runs this app's `scripts/child-app-init` (seeding is the app's own code there), pushes the tree and selects it; `pnpm child:down <slug>` runs `scripts/child-app-teardown`, which must revoke anything the child created outside the platform, then deletes it (README "Child Apps for Parallel Work").
- Before running other CLI commands, run `primitive whoami` to confirm the resolved environment, authenticated user, app ID, and server endpoint match this project.
- ALWAYS fetch the relevant guides before writing code that uses js-bao or js-bao-wss-client — the guides are the source of truth for how the platform works and are updated more often than this file. Run `primitive guides list` to see available topics and `primitive guides get <topic>` to retrieve one.
- If using Claude Code, the `primitive-platform` skill automates the guides workflow and validates your code against them. Install it with `primitive skill install`, and make sure it's loaded into your context before starting work in this project.
### Database types

- An app's data lives in databases (db3). Declare a type in `primitive/<env>/db3-types/<type>.toml` (beside the project config), push it with `primitive config push`, then run `pnpm codegen`: it generates `src/models/<type>/` (one class per model, plus that type's `allModels`) for every type file of the SELECTED environment, and rewrites `src/models/index.ts`, whose `allModels` the client is initialized with. Import a type's models from `@/models/<type>`. Fetch `primitive guides get databases` for types, records and access.
- With no types, `src/models/index.ts` exports an empty `allModels`; it is committed, so a fresh checkout type-checks before any codegen. Removing a type file removes its generated directory on the next `pnpm codegen`.

### Functions codegen

- Typed invokers for the app's server functions are generated from the `functions/*.toml` in the selected environment's tree: `pnpm codegen` runs `primitive functions codegen` into `src/types/generated/functions/` whenever that environment has functions. Each generated file exports a `<key>(client)` factory with typed `invoke` / `start` methods: call functions through it rather than `client.functions.invoke` with a string key.
- **Generated code is code**: everything `pnpm codegen` writes under `src/models/` and `src/types/generated/` is committed and reviewed like any other source, and nothing generated is gitignored. `dev`, `build`, `test` and `cf-deploy` all run `pnpm codegen` first, so a schema change plus any of them shows the regenerated output as a working-tree diff you commit with the change.
- NEVER edit generated files.
